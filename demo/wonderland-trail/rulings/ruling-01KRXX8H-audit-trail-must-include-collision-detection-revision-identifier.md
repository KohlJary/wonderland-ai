## Ruling 010: Audit trail must include collision-detection revision identifier

**GUID:** 01KRXX8H8ZFW6ANGP7T3NRRDRH
**Severity:** critical
**Domain:** logging-and-audit
**Source:** adr-audit-trail-schema-full-state-snapshots-with-timestamped-revisions

**Citation:**

OWASP A09:2021 Logging and Monitoring Failures; CWE-532 Insertion of Sensitive Information into Log File. Revision identifiers enable detection of concurrent writes and post-hoc reconstruction of the write ordering. Without them, two simultaneous saves produce an audit record that shows only the final state, masking which client's save won and whether data was lost.

**Finding:**

The audit_log table as proposed includes revision_id for collision detection, but the contract doesn't specify whether this revision_id is: (a) deterministic (hash of saved_state, so replaying the same save produces the same ID), or (b) non-deterministic (includes timestamp, random nonce, etc., so each save gets a unique ID even if content is identical). The choice affects whether concurrent saves can be disambiguated. If a user edits a note in two tabs and both post the same content (e.g., both tabs edited the same way), non-deterministic IDs let you tell them apart in the log; deterministic IDs do not. The collision-detection surface from the Cat's ADR requires that tabs can validate staleness by comparing revision IDs — but this only works if the ID represents the state at that moment, not a random token.

**Required Remediation:**

Clarify the revision_id generation strategy: specify whether it's a content hash (SHA256(title+body+tags+timestamp)) or a unique per-save token (UUID or timestamp-nonce). Content hash is deterministic and safer for collision detection (same save = same ID, so tabs can validate reliably). Unique-per-save is simpler to implement (just generate a new ID each time) but loses the ability to distinguish duplicate saves from concurrent edits. For v1 single-user, either works, but the choice locks the contract. Document the decision in the audit-trail schema ADR so the Tweedles know what they're building against.

**Acceptance Criteria:**
- The audit-trail ADR explicitly names whether revision_id is deterministic (content hash) or unique-per-save (UUID/nonce)
- The chosen strategy is justified in terms of collision-detection reliability and Kohl's use case
- The save-endpoint contract (M3) specifies what revision_id is returned and how it's used for staleness detection

**Residual Risk:**

If revision_id strategy is left ambiguous, the Tweedles will make independent assumptions during contract negotiation. One might assume content hash (deterministic); another might assume unique per save (nonce-based). When they integrate, the collision-detection logic will fail silently — tabs won't detect staleness correctly because they're comparing IDs generated by different strategies.

**Compliance Implications:**

GDPR Art. 5 (data integrity and confidentiality) requires audit logs to be reliable and trustworthy. An ambiguous revision_id strategy undermines log reliability because concurrent-write scenarios become uninterpretable from the audit trail alone.

**Audit Reference:**

This ruling locks the revision_id generation contract. The Tweedles' M3 save-endpoint contract must reference this ruling when specifying what the endpoint returns.
